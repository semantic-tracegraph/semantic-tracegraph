What this is

As agents take on more complex tasks, a single trajectory can contain several meaningful pieces of work. Most agent evaluations reduce that trajectory to a final pass/fail outcome. Although simple, that outcome hides useful intermediate progress, especially when the overall task fails.

Measuring the subtasks inside a trajectory gives us a richer view of agent behavior and a better way to understand cost per accomplishment. This matters in real-world use, where an agent may brainstorm, explore, diagnose, and implement within one open-ended session.

Semantic TraceGraph turns an agent trace into a small, evidence-grounded task graph. Each node represents an accomplishment supported by a consecutive span of events, and each edge records a causal relationship between accomplishments. In a coding trace, for example, one node might capture the search and reading that locate a relevant function, while a later implementation node depends on that earlier understanding.

How it works

Before decomposing trajectories, we need a shared ontology of the kinds of work they may contain. We call this ontology a graph spec. It defines reusable node types, their evidence criteria, valid edge types, and structural rules for the graph. The pipeline uses two agent workflows:

  • Graph spec construction learns a shared spec from a small calibration set of existing trajectories.
  • Trajectory decomposition applies that spec to a new trajectory to produce an evidence-grounded graph.

Spec construction has two stages. First, a type-blind segmentation agent divides each calibration trajectory into ordered, non-overlapping units of work without seeing any candidate ontology. Second, a spec construction agent compares those segments by intent, state transition, and evidence pattern. It clusters similar segments into node types and infers reusable causal relationships as edge types.

Decomposition follows the same boundary-first design. It reuses the type-blind segmenter on a new trajectory, then classifies the resulting work units against the learned spec. Consecutive segments may be merged when they form one accomplishment, and unmatched segments may be omitted. The final nodes retain their source segment and event IDs, keeping every claim traceable to the original trajectory.

Analysis

SWE-Bench trajectories

We ran an initial end-to-end test on SWE-Bench-style coding-agent trajectories. The calibration set contained 10 short, unresolved trajectories from a GPT-5 Mini coding agent. Type-blind segmentation produced 41 work units. The spec construction agent grouped them into four recurring node types: locate_and_inspect_code (12 segments), apply_fix (11), verify_behavior (10), and submit_change (8). It also inferred three dependency relationships: targets, validates, and packages.

We then applied that learned spec to one held-out SWE-Bench trajectory. The segmenter identified five work units, and the decomposer mapped them to five graph nodes connected by six edges. The graph captured a progression from locating an unencoded file read, to applying a UTF-8 fix, attempting verification, checking for related calls, and submitting the patch. This small run confirms that the learned spec can be reused on an unseen trajectory while preserving event-level evidence.

Cursor trajectories

We next applied the same pipeline to our own Cursor agent sessions. Local transcripts were converted into the shared trajectory format, then split at each user request so that a long multi-turn chat becomes several trajectories, each starting from one <user_query>. Seven conversations produced 275 such turns (median 5 events per turn, versus hundreds of events when a whole session is kept as one trace). Tool results are usually missing from the Cursor cache, so evidence is mostly tool invocations and assistant reasoning.

We calibrated on 30 of those turns, stratified across the seven conversations and mixing short and longer slices. Type-blind segmentation produced 80 work units. The spec constructor clustered them into an 11-type ontology, coding_agent_work_graph, with a typical order of survey_and_plan, setup_environment, implement_code, author_docs, repair_defect, verify_work, publish_code, administer_repo, execute_workload, diagnose_failure, and investigate_and_report. Compared with the SWE-Bench spec, this ontology is broader than locate/fix/verify/submit: it also covers environment setup, docs, git publish, repo administration, long-running jobs, and question-answering turns that do not change the workspace.

Decomposition of the same 30 turns produced 27 graphs (three timed out or failed to submit). Those graphs contain 55 nodes in total, usually one accomplishment per user turn (at most six). The most common types were investigate_and_report (10), survey_and_plan (9), and verify_work (8). That distribution matches the split: many Cursor follow-ups are a single question, check, or small edit rather than a full SWE-Bench issue.

Status

This is an early prototype with working ingestion, spec construction, segmentation, decomposition, verification, and evaluation. It currently supports SWE-Bench-style coding traces and local Cursor agent transcripts.

Using the prototype

Clone the repository, install with pip install -e '.[dev]', and set TRACEGRAPH_API_KEY. The CLI entry point is tracegraph (audit, sample, construct-spec, decompose, verify, evaluate). Details are in the README.
